# HyperPlayer 定调决策记录

> 定调会话产出（grilling），逐题确认，一题一记录。约束：不动代码；所有规划文档存放于 docs/。

## 已定

### D1 · 项目定位：认真开源项目（2026-08-29）

- 面向社区发布，需要认真考虑：许可证兼容、插件生态、文档、国际化
- 直接影响选型红线：Slint（GPL/商业双授权）、BASS（闭源、商用收费）等组件需要评估或排除

### D2 · 项目许可证：MIT（2026-08-29）

- 社区采用最友好，技术栈空间最大
- 选型红线随之收紧：**不引入 GPL 组件** —— Slint（GPL 双授权）默认排除；Qt 仅在 LGPL 动态链接可接受时保留（有摩擦）；BASS（闭源商用收费）排除
- MIT/Apache 系生态不受影响：iced、egui、GTK4（LGPL）、Go 系、Flutter（BSD）、Avalonia（MIT）

### D3 · 目标平台：只做 Windows（2026-08-29）

- 用户在知晓「只做 Windows 与认真开源定位存在张力（Linux 社区无缘）」的前提下仍选择单平台
- 换来的空间：SMTC 系统媒体控制、托盘、文件关联、WASAPI 独占等 Windows 深度集成可放心做；测试矩阵最小
- 对选型的影响：WinUI 3 / WPF / WinForms 等 Windows 专属方案重新进入候选；但 MIT 红线不变（Slint 仍排除）
- 注意：架构上仍建议保持平台适配层（系统集成独立封装），为未来可能的反悔留余地

### D4 · 开发者背景与 UI 诉求：Web/React 倾向，界面好看优先（2026-08-29）

- 用户自述想用 HTML + React 搞好看的界面；对 Flutter 有兴趣但存在认知偏差（以为 Flutter 能写 HTML/React），已澄清：Flutter = Dart + Widget 树，无 HTML/CSS，仅开发体验神似 React（声明式 + 热重载）
- 结论：放弃 React/HTML 代码本身，保留「类 React 的声明式开发体验」→ Flutter

### D5 · 架构红线升级：全禁 WebView，UI 框架 = Flutter Desktop（2026-08-29）

> ⚠️ **当日稍后被 D12 部分推翻**：WebView 解禁（限系统 WebView2），UI 改 React + TS。本条保留为决策史；现行红线见 D12 与 ADR-0002。

- **全禁 WebView 架构**：Electron、Tauri、Wails、WebView2 嵌入、本地服务+浏览器 一律排除——禁的是架构本身，不只是「打包 Chromium 太重」
- UI：Flutter Desktop（Dart + Widget 树，Skia/Impeller 自绘，BSD-3 许可与 MIT 兼容 ✓）
- **内存目标上调：20~100MB → 接受约 80~150MB**（用户在知情前提下用内存换 UI 表现力与开发体验；「轻量」定位相对 Electron 200~500MB 仍然成立，但不再是首要指标）
- Windows-only 不变（D3）；Flutter 桌面端集成弱（托盘/文件关联为二等公民）已知情接受，需要时走 channel/FFI 补原生
- Flutter 硬约束备忘：音频栈是最大短板（官方文档也承认桌面端偶有坑），选型需 PoC 实测

### D6 · 关键新信息：用户拥有自研 DSP，后续融入播放器（2026-08-29）

- 音频引擎选型新增硬约束：**管线必须为自研 DSP 预留插入点**
- 影响：全家桶引擎（libmpv/media_kit）与自有管线架构（解码→PCM→DSP→输出，如 miniaudio 节点图）的权衡重心改变——DSP 集成的顺畅度优先于「解码能力开箱即用」
- 音频引擎决策挂起，待确认 DSP 形态（语言/ABI/成熟度）后定
- DSP 的许可证与代码归属也需在定案时一并确认（影响 MIT 项目能否收纳）

### D7 · DSP 形态：TypeScript + Rust，正在收尾（2026-08-29）

- 用户自研 DSP 由 TS 和 Rust 两部分组成，Rust 侧接近完成
- 重要修正：用户实际掌握 **TS 和 Rust**（此前「Rust 学习曲线陡」的顾虑不成立）
- 引擎推荐随之翻转：**自研 Rust 音频引擎**（symphonia 解码 + 自研 DSP + cpal/miniaudio 输出，flutter_rust_bridge 桥接 Flutter UI）——DSP 原生融入管线，全栈 MIT/Apache 兼容，用户技能匹配
- 待确认：TS 部分在 DSP 中的角色（Flutter 无 JS 运行时，TS 无法直接跑在音频路径上）

### D8 · DSP 双线并行：TS 已可用，Rust 迁移收尾中，Rust 为准（2026-08-29）

> ⚠️ **2026-09-01 被 D29/D33 修订**：Rust 仍是唯一实时播放权威，但 TypeScript 不再整体退役；`shared/hse-ts-core` 保留为参数、预设、HSE2、预览、离线诊断和 parity 的非实时控制面实现。

- TS 版本当前可用，Rust 版本迁移接近完成——**Rust 是正式终态**，TS 随迁移完成退役
- 无「TS 功能困在 JS 运行时」问题，D5（全禁 WebView）不需要重审
- 音频引擎结论：自研 Rust 音频引擎（symphonia 解码 + 自研 DSP 插入 + cpal/miniaudio 输出），flutter_rust_bridge 桥接 Flutter UI——待用户显式确认（见待定项）

### D9 · 音频引擎定案：自研 Rust 引擎（2026-08-29）

- **Rust 音频引擎**：symphonia（纯 Rust 解码，MIT/Apache）+ 自研 DSP 插入 + cpal/miniaudio（输出，WASAPI；后续可扩展独占模式），编译为独立 Rust 库
- **flutter_rust_bridge** 桥接 Flutter UI 与 Rust 引擎
- 明确排除：media_kit/libmpv（管线控制权冲突，DSP 集成别扭）、just_audio（桌面端能力不足）
- 代价知情：播放队列、gapless、标签读写等播放器胶水层需要自建（symphonia 只管解码）；元数据解析用 lofty（Rust，MIT ✓）
- 与 D5/D6/D8 闭环：UI(Flutter) ↔ 桥 ↔ 引擎(Rust+DSP)，音频引擎独立线程，UI 只订阅状态

### D10 · 在线音源：官方内置（2026-08-29）

- 用户知情选择官方内置在线音源——**与三份报告的一致建议（本地为核心+社区插件）及 D1「认真开源」定位存在张力，版权与接口失效风险由项目自担**
- 工程底线（无论立场如何）：音源实现必须独立模块化（音源抽象层），可整体禁用/移除，不与播放核心、DSP 管线耦合
- 具体接入哪个平台/接口属详细设计阶段问题，定调不展开
- 待观察项：若未来收到平台方投诉或接口大面积失效，重审本决策

### D11 · v1 范围：全功能进 v1（2026-08-29）

- v1 = 本地完整体验（播放/曲库/封面歌词/主题）+ 自研 DSP 首发 + 内置音源
- 用户知情接受：战线最长、发布最晚、首发即带音源法律风险
- 缓解：音源模块独立隔离（D10），可先行开发、独立开关

### D12 · UI 层改案：React + TS 跑系统 WebView2，C# 薄壳（2026-08-29，推翻 D5 的 UI 部分）

> ⚠️ **当日稍后被 D13 推翻**（壳改 Electron 主进程、「禁打包 Chromium」红线删除）。本条保留为决策史；现行方案见 D13 与 ADR-0003。

- 经过：D5 后用户对 HTML/React 手感的偏好持续回弹（CEF 之问 → 微信/QQ 大厂参照），最终定案
- **红线修订**：由「全禁 WebView」收缩为「**禁打包 Chromium**（Electron / Tauri / CEF）」；**允许系统 WebView2**（Windows 10/11 内置，不打包内核，安装包零增量）
- **新 UI 栈**：React + TypeScript（Vite）↔ C# 薄壳（窗口/托盘/SMTC/媒体键/文件关联原生实现，无业务逻辑）↔ Rust 引擎（P/Invoke，cbindgen C ABI）
- 内存目标回落：**≤ ~100MB**（预期 50~90MB，优于 Flutter 方案的 80~150MB）
- CEF 评估结论：否——80~200MB 与 Electron 同级、C++ 壳/多进程/专有解码自编译，硬伤无补偿；Wails（Go 壳）亦否——多一门语言与 IPC 无增益
- 大厂参照：QQ NT = Electron（闲置 200MB+，专项优化后仍重）；微信 4.0 = C++/Qt 原生自绘（需大团队）；**网易云 PC 自身已由 CEF 迁往 Electron（2023，官方报道）——CEF 连原厂都在抛弃**；本方案 = QQ/网易云的 Web 开发体验 + 系统内核零包体 + 远低于 QQ 的内存
- **不受影响**：D1/D2/D3（定位/MIT/Windows-only）、D6~D9（Rust 引擎与 DSP 一等公民）、D10（内置音源）、D11（v1 全功能）

### D13 · 全面改案：Electron（2026-08-29，推翻 D5/D12 的壳与红线）

> ⚠️ **2026-08-30 被 D21 / ADR-0005 取代**。React + TypeScript UI 与 Rust 引擎方向保留；Electron 主进程、napi-rs、electron-builder 和“打包 Chromium”不再是现行方案。

- 决策：UI = React + TypeScript；壳 = **Electron 主进程（Node/TS）**——用户全程只需 TS 一种语言
- **立项前提正式作废**：三份调研报告的「反 Electron / 轻量化」约束不再作为选型红线，报告降级为史料与功能清单参考；「禁打包 Chromium」红线删除
- 定位改写：「轻量级播放器」→「**现代化 Windows 音乐播放器，差异化 = 自研 DSP**」
- 内存指标作废：≤100MB → 不设硬指标；现实预期空闲 150~250MB、播放 200~400MB（参照 QQ NT 专项优化后闲置 ~200MB），工程上做常规优化即可
- Rust 引擎保留（D9 不变），桥接改为 **napi-rs**（Node↔Rust FFI）：React ↔ Electron IPC ↔ Node 主进程 ↔ napi-rs ↔ Rust 引擎
- 生态收益：electron-builder 打包、自动更新、崩溃上报、DevTools 白送
- Tauri 曾在内心评估：Rust 壳与用户技能匹配且轻量，但 IPC/插件生态摩擦大于 Electron，且用户在知悉 QQ/网易云案例后主动选择 Electron 生态——记录在案
- **不受影响**：D1（认真开源）、D2（MIT，Electron MIT ✓）、D3（仍只发 Windows，跨平台能力白送留作未来）、D6~D9（DSP/Rust 引擎一等公民）、D10（内置音源）、D11（v1 全功能）
- 演进史（截至当时）：D5 Flutter（当日推翻）→ D12 WebView2+C#（当日推翻）→ D13 Electron（随后被 D21 取代）；共同点 = 用户对 React/TS 路线的持续确认

## 详细设计阶段（D14 起）

### D14 · 应用核心归属：Rust 拥有「文件→数据库」整条链（2026-08-29，D21 后继续有效）

- **Rust 引擎/领域库三层能力**：① 音频引擎（symphonia 解码 → DSP 管线 → cpal/miniaudio 输出）；② 曲库扫描（目录遍历 + lofty 元数据/封面解析）；③ SQLite 存储（rusqlite，曲库索引、播放记录）
- **桌面框架应用层 = 纯编排**：Tauri commands/events、系统集成（托盘/SMTC/文件关联）、音源协调、生命周期管理——不碰大文件 IO，不承载领域规则
- **React/WebView = 纯 UI**，一切数据经 Tauri commands/events/channel 获取
- 理由：万级曲库扫描/解析/入库全在 Rust 线程域内完成，WebView 前端零阻塞；文件 IO 不跨语言搬运；lofty（D9 钦点）顺势落位；用户具备 Rust 能力
- 代价知情：曲库查询、扫描进度、播放状态需设计稳定的 serde DTO 与 command/event/channel 契约（详见 ADR-0004）

### D15 · 音源平台 v1：网易云 + Cleanroom 开发（2026-08-29）

- **v1 内置音源只接网易云**；音源抽象层（Source Module 接口）照 D10 设计好，后续平台是增量活
- **用户将提供其他项目的逆向参考代码**（网易云 API + 歌词接口），供阅读研究
- **Cleanroom 硬约束（用户明令）**：实现必须独立编写——流程为「读参考代码 → 提炼行为规范文档（接口/参数/流程/算法行为）→ 只按规范实现」；参考代码与实现代码永不同场
- **参考代码存放 `docs/reference/`**（已被 gitignore）：第三方逆向代码**永不入库**，避免污染 MIT 许可
- 在线歌词获取同属网易云接口范畴，遵循同一 Cleanroom 规则
- **执行进展（2026-08-29 晚）**：参考代码由用户置于 `temp/netease-lyrics-code/`（7.8 万行完整项目，仅提炼网易云 API + 歌词行为）；规范文档 `docs/音源-网易云-行为规范.md` 已产出
- **全量开发（2026-08-29 深夜，用户明令「别少，全量开发」）**：94 条参考路由全部覆盖 → `src/audio-source/netease/`（config/crypto/session/request + core/catalog/social/user/explore 五客户端，115 个导出函数）+ `src/audio-source/lyrics/`（LRC/YRC/TTML 解析器 + 词级时间归一化/卡拉OK图元），共 ~3400 行，`tsc --strict` 零错误、运行时零第三方依赖。协议要点全部按参考库行为落位：eapi 默认加密（interfacepc 域）、xeapi 安卓加密（X25519+AES-GCM 会话）、设备 cookie 信封、匿名注册链、评论资源前缀表、歌单收藏防作弊 token、nos 封面上传、512 重试、playlist_track_all 分页、FM 批量去重、journey/explore 聚合
- **明确排除**：song_url_match/unblock 跨平台备用音源（与付费内容规则冲突）；QRC 解密（网易云不需要，未来接 QQ 源直接用 MIT 库 qrc-decoder）
- ⚠→✅ **联网 PoC 已完成（2026-08-30）**：匿名链路（公钥→匿名注册→搜索→歌词→播放地址）+ 广度扫描 11 项**全部实测通过**（播放地址命中真实 CDN）；过程发现并修复 4 处实现缺陷（xeapiSign 密钥用法、XOR 模 16、外层 /api 前缀、weapi 通道被 WAF 空响应——已全量改走 eapi 通道绕行），详见规范文档 §8 实测记录。匿名注册存在鸡生蛋问题（无 MUSIC_A 被拒），已实现 tmp 种子读取+静默降级，核心端点实测不依赖 MUSIC_A

### D21 · 桌面壳改为 Tauri 2（2026-08-30，取代 D13 的 Electron 壳）

- **现行技术栈**：Tauri 2 + React/TypeScript + Vite + Rust engine；Windows 使用系统 WebView2，不再打包 Chromium

### D23 · VIP 缓存必须绑定登录账号与实时会员权益（2026-08-30）

- **普通免费缓存域 `Public`**：只包含服务端确认可免费完整播放的歌曲，可按最近 100 首滚动缓存规则跨匿名/登录状态复用
- **VIP 缓存域 `AccountEntitled(userId)`**：VIP/付费权益歌曲缓存必须绑定创建它的网易账号 ID；不能转为公共缓存，不能被其他账号复用

- 登出/过期不要求立刻物理删除缓存文件（避免频繁写盘），但其状态转为 `LockedEntitlement`，进入较高淘汰优先级；重新登录同一账号且权益恢复后可重新授权
- 缓存元数据必须记录 `accessClass`、ownerUserId、entitlementSnapshot、lastValidatedAt、contentId/quality、officialSource；不得只靠文件存在判断可播放
- VIP 权益结果只能由 Rust 后端根据网易服务端响应计算；React 不得传 `isVip: true` 绕过门禁
- 本决定不等于允许音乐下载或导出；缓存仍为应用私有、不可浏览/另存、无媒体扩展名的受控播放缓存

### D24 · 专辑播放缓存：下一首预取 + 高频专辑空闲补全（2026-08-30）

- **策略一始终启用：下一首预取**。当播放来源上下文为专辑时，当前曲播放期间提前缓存并预热下一曲；切歌后窗口随队列前移。目标是下一曲网络读取、解码器初始化和首段 PCM 均在当前曲结束前完成
- **策略二按热度晋升：全专辑缓存**。同一专辑累计完成第 5 次“有效专辑会话”后标记为高频专辑；此后仅在系统/网络/音频管线空闲时，以低优先级补齐整张专辑缓存
- **有效专辑会话定义**：必须从专辑页或明确的专辑播放上下文发起，并满足「累计完整播放至少 1 首」或「累计有效播放达到 5 分钟」之一；同一专辑同一自然日最多计 1 次。搜索单曲、歌单、随机电台和手动临时队列不计入
- **调度优先级**：当前曲 > 下一曲预取 > 再下一曲预热（若资源允许）> 高频专辑剩余曲目。播放中网络/磁盘忙、计费网络、低电量或磁盘压力时暂停全专辑后台补齐，但下一首预取保持高优先级
- **切换行为**：用户离开当前专辑、改变队列或跳到其他上下文后，取消尚未开始的旧专辑低优先级任务；已完成文件保留在普通缓存池，未完成 partial 安全删除或等待恢复策略处理
- **去重与归属**：两种策略共享同一 content-addressed 文件，不重复落盘；使用 lease/reference 标记 `NextTrackPrefetch`、`AlbumPrefetch(albumId)`、`RecentHistory`
- **VIP 联动（D23）**：VIP 曲目的下一首预取与全专辑补齐都必须先通过 `AccountEntitled(userId)` 权益门禁；后台任务启动、断点续传和最终播放前都要确认同账号权益。失效后转 `LockedEntitlement`，不播放、不继续补齐
- **不是下载**：全专辑缓存不创建用户可见目录、无歌曲名/扩展名、不提供导出或另存；受容量和 LRU 淘汰约束，不承诺永久存在
- **真正无缝播放的额外条件**：缓存完成只是网络层准备；Rust 引擎还必须提前创建 standby decoder、处理编码 delay/padding、统一 PCM 格式并预填 ring buffer，在采样边界切换。仅把文件缓存完整不能宣称 gapless
- 尚待定：总缓存容量、最近 100 首是否严格上限、完整播放判定阈值细化、断网行为和后台任务资源阈值

### D32 · DSP 配置生命周期与实时边界（2026-09-01）

- DSP 配置使用 `requested → prepared/ready → applied → retired` 生命周期。前端和 Tauri 必须提交非零、严格单调递增 revision；缺失、零值、重复或倒退 revision 在进入处理链前拒绝
- 同一个非空 active PCM 块边界前连续到达的配置采用 latest-config-wins：较新 revision 覆盖尚未应用的 ready chain，可跳过中间 revision；实际应用过的 revision 始终严格递增
- ready chain 只能在 active PCM 的非空块边界执行一次常数时间句柄交换。空块、尾部 drain 和 standby 预处理不能消费 ready revision；standby 晋升为 active 的采样边界可以应用
- 参数解析和轻量合法性校验在命令路径同步完成；播放期间的 processor 构造、系数计算和工作缓冲分配进入单独的有界 latest-wins 编译 worker，停止/未播放时可同步准备。被覆盖 ready chain 的析构在非实时 actor 路径完成；已准备且符合 block contract 的正常块处理路径不得分配、等待锁或输出日志，输入契约和处理器故障仍由 actor 路径显式捕获。旧 active chain 进入 retired 槽，由后续非实时回收点析构
- 当前已迁入 12 阶段链的 prepare 成本为 `O(阶段数 + EQ 段数 + 最大块样本数 + Delay/Chorus/Flanger 环形缓冲样本数)`，最大块固定 2048 帧、EQ 最多 20 段、三类延迟效果的双声道环形缓冲在 prepare 前一次分配；Phaser 使用固定 16 槽/声道状态，不增加随块长变化的分配。扩展到完整 22 阶段时继续沿用单槽 pending/ready 覆盖，禁止形成无界编译或结果队列
- standby DSP 预处理属于 speculative 状态推进：chain 在 prepare 时预分配 runtime checkpoint，standby 正常 promotion 显式提交；缓存失效、队列丢弃、配置 revision 重算或处理故障时零分配恢复全部状态型 processor 与 fault 快照。revision replacement 只迁移运行时状态，不覆盖新参数/系数；disabled→enabled 按 HSE 重置，禁止嵌套 checkpoint
- Delay 等反馈效果的 `tail_frames` 表示不含 latency 的自然衰减估算；串联链按加法聚合。Phaser 的递归 IIR 无有限自然尾，处理器报告比 12 秒上限多一帧的保守值以明确触发 transport 截断。非 gapless 终曲最多排空 12 秒，只有自然尾超过上限时才在最后 2 秒施加等功率淡出；gapless continuation 不插入尾音或淡出
- prepare/校验失败时保持当前 applied chain 和音频输出不变，不在处理路径尝试降级、重建或回退。同步轻量校验错误直接返回调用方；播放期间异步 prepare 只接受已通过校验的有界配置，异常结果不进入 ready，后续通过 DSP 状态桥暴露失败 revision
- 首曲源格式不再决定设备声道布局：CPAL 从默认设备支持范围选择双声道 F32 输出，优先设备默认采样率、其次 48 kHz、否则取最近支持边界；mono 与其他源格式由 `PcmAdapter` 转换，保证 stereo DSP 能力不会因首曲为 mono 而永久失效
- CPAL 数据回调使用预分配的无锁有界环，只执行原子 pop、音量乘法和欠载零填充；错误回调只设置原子故障标志，字符串格式化和错误传播留在 engine actor
- `PlaybackSnapshot.revision` 是离散 UI 状态版本：加载、ready、暂停、恢复、seek、stop、fail、音量和队列/模式变更均递增，周期进度不递增。Tauri 的 `EngineSnapshotDto` 原子携带同 revision 的 playback 与 queue；前端只以该事件/命令响应为权威状态，并拒绝旧或重复 revision
- DSP 异步 prepare 拒绝与首次 processing fault 使用独立关键事件上报；progress 可节流/丢中间帧，关键状态和故障事件不得被 progress 合并覆盖

### D33 · HSE Rust 主链、TypeScript 功能降级与重复内核退役（2026-09-01）

- HyperSoundEngine v1.5.1 自带 Rust 核心是 HyperPlayer 唯一的生产 DSP 算法主实现；继续按播放器实时契约修改和适配，不再以 HSE TypeScript 代码为模板重复手写一套 Rust 算法
- `shared/hse-ts-core` 作为非实时控制面的备选/降级实现，承担参数与默认值校验、12 场景、HSE2 编解码、响应曲线预览、离线诊断和 Rust/TypeScript parity；控制桥尚未连接或可视化不可用时，可用 TS 保持这些非播放功能可用
- TypeScript 不作为实时音频后备引擎，不通过 Web Audio、AudioWorklet、WebView 脚本或原始 PCM 跨 IPC 接管播放。Rust 链处理失败时继续恢复输入块并进入零 DSP `SafeBypass`，播放、gapless、设备输出和故障恢复仍全部由 Rust engine 负责
- `hyperplayer-engine` 中原先按 TypeScript 另行编写的 Rust 算法按阶段退役。每阶段固定顺序为：vendored core API → `PcmProcessor` adapter → vector/parity → revision/checkpoint/standby → 零分配门禁 → 全量测试 → 删除重复算法主体
- 最终只允许 HyperPlayer 保留产品适配代码：interleaved/planar PCM、enabled 门控、格式/有限值校验、revision、checkpoint、standby speculative state、latency/tail、sidechain 路由、fault safe-bypass 和实时线程约束。采样级 DSP 算法、系数设计、状态推进和参数默认值应由 vendored HSE core 单一维护
- 在某阶段尚未满足 checkpoint、状态迁移、尾音或零分配契约前，可暂时保留现有实现，但必须标记为迁移中的兼容层，不得宣称去重完成；迁移完成后删除对应重复文件和测试入口，不保留两套可达生产路径
- TypeScript parity 直接使用 `@hyperplayer/hse-ts-core`；仅当 vendored TS core 没有可独立调用的 stage API 时，才允许保留最小测试 adapter，并在 Rust core API 可用后同步删除

### D35 · 前后端接缝定调（D34 补课，2026-09-04 第二轮 8 问）

**八条定案**：

1. **SMTC/媒体键（Q13=a）**：WebView 权威 + Rust 纯桥。上行：TS 推送 `smtc_update_metadata` / `smtc_update_playback_state` / `smtc_update_position` 三个 command；下行：媒体键化为 `media_button_pressed { button }` 事件发到 WebView 由前端播放服务执行；Rust 现有 SMTC 按钮直调 `state.services.playback` 的处理器改为 emit 事件，Rust 零播放知识。

3. **缓存介质（Q15=a，含附加约束）**：OPFS（Origin Private File System）——用户不可见、无文件扩展名语义，严格执行「不暴露 MP3 文件」红线；容量治理（iterate/hash 淘汰）纯 TS。**用户附加约束：缓存数据必须跟随程序走**——WebView2 数据目录钉在应用自身数据目录（随安装/卸载/升级），存储位置/容量/清理入口在应用内设置页说明；占用记账走 `navigator.storage.estimate()` + TS 自身记账双轨。

5. **Cookie/会话存储（Q17=a）**：**保留 Rust DPAPI 保险库**（`credential_vault.rs` 从 D34 删除清单摘出），作哑加密存储——TS 经 2 个 command 存取（内存持有、写入 DPAPI 加密落盘），防「数据目录被拷贝盗号」档位，与 D34.7 降档威胁模型匹配；cookie 语义归 TS，加密机制归 Rust（与哑 KV 同性质）。
6. **多窗口状态广播（Q18=a）**：主窗口权威 + Tauri event 广播——播放状态（曲目/播放态/进度/歌词行）经 `app.emit` 跨 WebView 窗口推送（进度 1Hz 节流、歌词行按行触发，整篇歌词文本辅助窗口本地缓存）；桌面歌词/迷你播放器纯订阅渲染、零业务逻辑；控制回传走 command 转发到主窗口播放服务。

## D36 · Node sidecar 重定调（2026-09-05 用户定调，修订 D34 Q2/Q3）

> 用户指令原话：「为了加快开发进度 允许你使用node了 可以把相关限制解除掉 … 再看一下 neteaseenhanseapi 那个玩意 直接用node 把那个原来应该用node接入的包原生接入 去除你自己写的shims和适配层 功能实现保证优先」。直接诱因：浏览器化适配层的自写 shim 链（axios shim / node-globals / 同步 crypto 等价实现）成为连续故障源（匿名 xeapi 公钥链失败 → 搜索/发现页全空），且未来每一处协议细节都要在 shim 层重复对齐。**功能实现保证优先**。

**定案**：

1. **「零 Node 运行时」条款解除（修订 D34 Q2）**：产品壳仍不引入 Electron/Node sidecar 之外的运行时捆绑；**网易云协议层允许本地 Node sidecar**。开发期用系统 Node（≥22）；打包期需捆绑 node.exe + 脚本资源并由 Rust 壳托管进程生命周期（M6 打包定稿，本轮不阻塞）。D21「拒 sidecar」条款就此对协议层失效，对播放/DSP/壳层仍有效（播放链、HSE、SMTC 不变，仍全在 WebView + Rust 壳）。
2. **协议包原生接入（修订 D34 Q3「三处手术」）**：`vendor/netease-cloudmusic-api` 不再做浏览器化改造——作为标准 Node 包安装自身依赖（pnpm workspace 成员），以自带 `server.js#serveNcmApi` 起 express 服务（dev 端口 `14321`），**三处手术全部作废**：axios/加密/fs/express 自动发现全部回归 Node 原生。匿名身份（anonymous_token / xeapi 公钥）由包的 `generateConfig` 原生流程自管（文件落 os.tmpdir；打包期改指应用数据目录，随 node.exe 捆绑一并处理）。
3. **适配层删除**：`app/services/netease/shims/**`（11 文件）、`app/services/netease/generated/**`（浏览器 bundle + 静态枚举 registry + d.ts）、`scripts/build-netease-vendor.mjs`、package.json `build:netease-vendor` 链全部删除；`temp/` 下探针脚本保留（gitignore）。
4. **前端服务层传输切换**：`neteaseService.call()` 从「进程内 apiMap 调用」改为 **sidecar HTTP**——`POST http://127.0.0.1:14321/{module}`，参数 JSON body，`cookie` 字符串随 body 传（server 路由原生 `cookieToJson` 注入），响应 `{status, body, cookie}` 形状与原 shim 语义一致；20s AbortSignal 超时。会话主权不变：MUSIC_U 仍在前端（DPAPI 保险库），sidecar 不持久化登录态。传输走 `tauri-plugin-http`（绕 CORS，scope 补 `http://127.0.0.1:**`/`http://localhost:**`——D35 Q19 的 HTTPS 任意域之外新增本机回环明文，偏差如实记录：回环内本机进程间通信）。
5. **WaveForge 业务层留在 TS**：音质阶梯降级/付费拦截/重试已按 WaveForge 语义移植在 `neteaseService`（getSongUrl 阶梯、fee 如实返回、无跨平台兜底），本轮不动；后续若上移到 sidecar 另行定调。
6. **红线重申**：`ENABLE_GENERAL_UNBLOCK` 不启用；`song_url_match`/跨平台匹配/unblock 行为红线不变（vendored 包的 general unblock 路由默认关闭，sidecar 不设置该 env）。`@neteasecloudmusicapienhanced/unblockmusic-utils` 是包自身依赖（MIT、同 publisher），仅被已排除模块引用、运行时不加载行为路径——在 THIRD_PARTY_NOTICES 登记即可，不构成红线违反。
7. **dev 编排**：`pnpm dev` 改为 `scripts/dev.mjs`（Node 编排器：并行起 sidecar + `tauri dev`，随宿主退出清理）；sidecar 单独入口 `pnpm sidecar`。

**对既有文档的影响**：AGENTS.md「硬性约束」「目录结构」「技术栈」「构建/测试」相应条款同步修订；本条目落档后 D34 Q2「零 Node 运行时」、Q3「三处手术」、D35 Q19 的 scope 面（新增回环 http）以本条为准。
