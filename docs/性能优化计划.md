## 0. 结论速览

### 三句话结论

1. **清单里约一半的措施本仓库已经达标或本就不适用**（见 §1 对照表），别重复劳动。
2. **最大单项收益在启动链路**：总启动 ≈7.4s，其中「后端就绪」占 3.6–3.9s，而这 3.6–3.9s 的主因已定位——`local-server.mjs` 在模块加载末尾就同步拉起网易云 API 库（**19 MB / 431 个模块文件**，其 `main.js` 用 `readdirSync` 逐个 require）**外加两次网络请求**，全部堵在主进程每 150 ms 一次的 `/health` 轮询窗口里。把它移出启动路径，**预计总启动 7.4s → ~4.5s**。
3. **运行时最大单项在渲染侧**：每次切歌的交叉淡化（8–12 秒）期间，`App.tsx`（**6,589 行**）会以 30 fps 全量重渲染——因为过渡进度是 App 顶层 state。仓库里已有现成解法（外部 store + `useSyncExternalStore`）。

## 3. 阶段 1：启动链路（预期 7.4s → ~4.5s）

### 3.1 后端网易云 API 延迟初始化 ★ 最大单项

**现象与证据**

- `local-server.mjs:1661` 定义 `initNeteaseAPI()`；**`local-server.mjs:1686` 在模块加载末尾直接调用它**。
- 它做两件极重的事：
  1. `await import('@neteasecloudmusicapienhanced/api')` —— 该库 **19 MB**，`module/` 下 **431 个 `.js`**，其 `main.js` 用 `fs.readdirSync(modulePath)` **同步逐个 require**；
  2. `await generateConfig()` —— **两次网络往返**（`register_anonimous()` 注册匿名 token + `getXeapiPublicKey()` 拉公钥）。
- 主进程此时正以 **150 ms** 间隔轮询 `/health`（`desktop/main.cjs:4320-4351`），启动页门控上限 4500 ms（`1939`）。**这 431 个模块的同步加载与网络请求，正堵在 /health 的响应窗口里**——这就是「后端就绪要 3.6–3.9s」的主因。
- 而 `/health` 的健康契约（`server/local-api-health.mjs`）**只校验 `status/service/protocolVersion`，不要求网易云已加载** → 延迟初始化**不会**影响就绪判定。

**改法**

1. 引入记忆化就绪入口 `ensureNeteaseReady()`（内部只启动一次 `initNeteaseAPI()` 并复用同一个 promise；`initNeteaseAPI` 自带 try/catch，失败不抛）。
2. 删除 `1686` 处的模块级调用。
3. `/health` 处理函数里**先 `res.json(...)` 写出响应**，再用 `setTimeout(…, 500)` 安排初始化——确保健康响应真已刷出、主进程已拿到，再去抢事件循环。用一个布尔量保证只安排一次。
4. 给网易云路由加一层「就绪门」：`app.use(<netease 前缀集合>, async (req,res,next) => { await ensureNeteaseReady(); next() })`。
   ⚠️ **Express 按注册顺序执行**：该中间件必须注册在**所有网易云路由之前**（现有 CORS/token 中间件在 `1037-1067`，网易云路由从 `1700+` 开始），否则对已注册路由不生效。
5. 保留既有的 `if (!NeteaseAPI || !NeteaseAPI.xxx)` 守卫（它们成为「初始化失败」的兜底，语义不变）。

**为什么零回归**：所有网易云路由都会 `await` 就绪（原来是「未就绪直接报错」，现在是「等一下，然后正常服务」）；初始化失败时 promise 正常 resolve、守卫照旧报错，与今天一致。

**验收**：`[Electron +Nms] Local backend ready after Xms` 应显著下降；随后手测网易云取歌/歌词/歌单/扫码登录与 QQ/B 站路径；`npm run test` + `npm run test:desktop`。

### 3.2 V8 编译缓存（Node 原生能力）

**证据**：Electron 42.8.0 = Node 24.18（支持 `module.enableCompileCache()` 与 `NODE_COMPILE_CACHE`）。后端 `local-server.mjs` **11,159 行 / 439 KB**，加上 431 个网易云模块，每次冷启动都要重新解析编译。

**收益**：**第二次及以后**的冷启动省掉上述模块的解析编译。**风险**：极低（缓存失效自动重建；目录在 `%APPDATA%/HyperPlayer` 下，不污染仓库、不新增依赖）。

**验收**：连续冷启动 3 次，看第 2、3 次的 `Local backend ready after Xms`。

### 3.3 后端孤儿清扫快路径

**证据**：`sweepBackendOrphans()`（`main.cjs:4293-4313`）对 3211 端口 spawn `powershell -NoProfile -Command "Get-NetTCPConnection …"`（timeout **12000**）再 `taskkill`（timeout 8000）；而 `startLocalBackend()` 是 **`await sweepBackendOrphans('startup')` 之后才 fork 后端**（`4359`）——PowerShell 冷启动被**串行**塞进启动路径；`will-quit`（`4392`）还会再跑一次，拖慢退出。

**改法**：跑 PowerShell 之前先做**廉价 TCP 探测**（`127.0.0.1:3211`，~250 ms 超时）：

- **没人监听 → 不可能有孤儿 → 直接跳过 PowerShell 与 taskkill**（记一行 `Backend port 3211 free, orphan sweep skipped`）；
- 有人监听 → **走原来的 PowerShell + taskkill 逻辑，一个字不改**。

**收益**：正常启动省 0.5–1.5s（PowerShell 冷启动），退出更快。**风险**：极低（无监听即无孤儿，语义等价）。**注意**：探测 socket 必须在所有分支 `destroy()`，否则会拖住事件循环、阻止进程退出。

### 3.4 次要项：启动期同步读合并（低优先，可延后）

`whenReady()` 里仍有若干同步小文件读取与 `existsSync`/`mkdirSync`（`4400-4401`、`4498`、`4503-4516`、`4796-4799`）。单次成本很小（都是 KB 级 JSON），**收益远小于 §3.1–§3.3**，建议只在顺手时合并（例如 4 次 `existsSync`+`mkdirSync` 合并为一次 `mkdirSync(recursive)` 调用）。**不要为此专门重构启动流程**。

## 4. 阶段 2：稳态开销（P0/P1，多数无行为变化）

### 4.1 媒体协议（`hyperplayer-media://`）的同步文件 I/O

**证据**：`registerMediaProtocol()`（`main.cjs:2469-2485`）每次请求都 `fs.existsSync(filePath) || fs.statSync(filePath).isFile()` —— 同步 I/O 打在主进程事件循环上。而该协议正是「渲染进程读取已下载音频文件做分析」的通路（`desktop/audio-download.cjs:635`、`src/services/autoMixAnalysisService.ts`），属热路径。

**改法**：先做内存白名单判断（`allowedMediaFiles.has(filePath)`，保持同步且最先）；通过后用 `fs.promises.stat` 异步校验（`callback` 允许异步调用），错误码语义保持不变（不存在/非普通文件 → `-6`，异常 → `-2`）。

**收益**：中（主进程事件循环不再被磁盘 stat 阻塞 → 不拖累所有窗口与 IPC）。**风险**：低。

### 4.2 缓存写放大（「读一次写一次」）

**证据**

- `src/services/cacheManager.ts:220-226`：`getCachedCover()` **每次读命中**都 `JSON.stringify(item)` + `localStorage.setItem()` —— 同步写盘，而 item 里含 base64 图片（单图上限 10 MB，见 `src/tv/perfMode.ts:94-101`）。
- `src/services/indexedDBCache.ts:131-134` / `196-198`：`getCoverBlob()` / `getData()` **每次读命中**都开一个 `readwrite` 事务把**整条记录（含 Blob）重写一遍**。

**改法**：把「访问统计」改成**内存累计 + 节流落盘**（~30 秒一次 + `visibilitychange`/`pagehide` 时 flush）。**所有对外语义保持不变**：返回值、过期判定与过期删除、命中判断都不变；只有 LRU 统计（`accessCount`/`lastAccess`）允许滞后一个 flush 周期——这是该优化的必然取舍，需在代码注释里写清。

**收益**：中–高（歌单滚动/反复切歌时消除大量同步 localStorage 写与 IDB 整条重写）。**风险**：低（仅影响近似 LRU 的精度）。

### 4.3 后端 SSRF 检查的 DNS 每请求解析

**证据**：`isBlockedFetchUrl()` 在 `local-server.mjs:1398-1406` 每次调用都 `dns.promises.lookup`（外层 3 秒超时竞争）；调用点：`/api/audio`（`1422`）、`/api/cover`（`1469`）、`/api/proxy-image`（`1592`）——即**每个音频/封面代理请求一次 DNS 解析**。

**改法（保守）**：只对「解析成功且所有地址都是公网」的结论做**短 TTL（60s）、有上限（200 条）**的正缓存；**私网/被拒/解析失败/超时分支一律不缓存**，判定逻辑与保守拒绝语义一字不改；字面 IP 快速路径不动。

**收益**：中（播放与封面加载省一次 DNS 往返）。**风险**：低–中（安全敏感区：缓存只存「公网」结论且 TTL 很短，DNS rebinding 风险与现状同级——现状也是「解析一次即信」）。**若对语义有疑虑，宁可不做。**

### 4.4 热路径 `console` 噪音

**证据**：`src/components/SearchPanel.tsx:116-119` 在**渲染函数体内**有 4 条 `console.log`，而该组件没有 `React.memo` → 父级每次重渲染都执行；另有若干组件在每次切歌/数据变化时打印**整个 payload 大对象**（`ArtistDetailModal` ≈18 处、`DesktopView` ≈11、`ProfileView` ≈8、`BilibiliMvBackground` ≈9、`HomeView` ≈3）。`src/main.tsx:33-45` 还把每条 `console.error` 序列化后转发 IPC。

**改法**：渲染体内的 `console.log` 直接删除；每次数据变化都打的改 `debugLog()`（仓库既有门控，默认静默，`src/utils/debugLog.ts`）；`console.error` 的 IPC 转发加频次限制（同文本 2 秒一次 + 全局每分钟 10 条，被抑制的条数在下一条里带出）。`console.warn`/`console.error` 本身一律不动。

**收益**：低–中（消除每帧字符串构造与 IPC）。**风险**：极低。

### 4.5 `resize` 监听 rAF 合并

**证据**：12 处裸 `window.addEventListener('resize', …)` 未做帧合并（`DesktopWidgetZone:605`、`FontPicker:133`、`TraditionalView:465`、`PlaylistGrid3D:239`、`SongContextMenu:214`、`desktop-lyrics/DesktopLyricsApp:198`、`desktop-player/DesktopPlayerApp:234` 与 `476`、HSE 的 `SpatialModeVisual:195`/`SpatialRingEditor:337`/`SpatialWorldView:681`/`WaveformVisualizer:40`）。窗口是无边框自绘标题栏、可拖拽缩放，**缩放时会连续触发大量 resize 事件**，处理函数同步测尺寸 → setState → 重渲染。仓库里已有 rAF 合并的先例（`PlaylistDetailPanel.tsx:203-215`、`ScrollToTop.tsx:39-48`）。

**改法**：新增 `src/utils/rafThrottle.ts`（含 `cancel()`），在每个 `useEffect` 内包裹 resize 回调，**只包裹 resize 这一条路径**，其余监听与依赖数组原样不动；清理时 `cancel()` 防止卸载后执行。

**收益**：中（缩放窗口更跟手）。**风险**：低。

### 4.6 IPC 频率与批处理

**证据**：灯效帧推送 `chroma:frame`（`desktop/chroma-ipc.cjs:550`）由渲染侧按 15/30 fps **逐帧、逐设备**发送（`src/plugins/clients/ChromaClient.ts:409`）；主窗口侧仍有 10 Hz（100 ms）的频谱 loop（`App.tsx:4395-4520`，已做变化去重）；任务栏小窗 120 ms 轮询（`desktop/taskbar-widget-polling.cjs:3`，仅可见时）+ 状态推送 1000 ms 去重（`main.cjs:1636`）。

**改法**：同帧多设备合并为一条 IPC；把 10 Hz 推送上限进一步降到 ~5 Hz（沿用现有变化去重）；hover 状态仅在变化时发送。

**收益**：低–中（灯效开启时明显）。**风险**：低。**注意**：Chroma 侧有既有测试（`test/chroma*.test.ts`、`scripts/test-chroma*.cjs`），改动后必须跑通。

## 6. 阶段 4：音频与深度改造

### 6.1 AutoMix / MV 分析搬出主线程（两步走）

**证据**

- `src/services/autoMixAnalysisService.ts`：`analyzeBuffer`（`733-819`）在主线程同步跑完整 DSP —— `computeFrameEnvelope`、`detectTempo`（`180-224`，O(lags×n)）、`spectralFeatures`（`169-178`，**每拍 49 次 Goertzel**）、`buildSections`（`609-632`）；`toMonoDownsampled`（`639-661`）是逐样本/逐声道循环；`findBeatPatternGrid`（`370-505`）滑窗约 1800 次打分；`envelopeOffsetOf`（`519-567`）每次新建数组。
- `src/hooks/useAudioPlayer.ts:977-980`：**在播放中**用 `Promise.all` 同时对「当前曲 + 下一曲」跑上述分析。
- `src/services/mvAlignment.ts:237`/`549-600`：MV 对齐还会再对 MV 与歌曲各解码一次。
- 全仓**没有任何 Web Worker**。

**关键约束（避免实施时走错路）**：**Worker 里没有 `AudioContext`**，所以 `decodeAudioData` 必须留在主线程（它本身是原生异步、不占 JS 线程）。**只有 PCM 之后的 DSP 可以搬**。也不要指望 `OfflineAudioContext` 能进 Worker——同样没有。

**改法分两步**

- **6.1a 调度降干扰（先做，低风险）**：把「下一首预分析」安排到 `requestIdleCallback` / 过渡完成之后 / 暂停时；避免在播放中并发跑两首全曲 DSP。**只改时机，不改结果**。
- **6.1b Worker 化（后做，中高风险）**：主线程只保留 `fetch` + `decodeAudioData`，把 PCM（`Float32Array`，transferable）传给 Worker 跑 envelope / tempo / Goertzel / beatFeatures / sections，回传纯数据。`planTransition` 的输入不变 → 过渡窗口与增益曲线不变。

**验收**：`npm run benchmark:mv` 的语料做**分析结果等价性对比**（阈值内一致）+ 现有 vitest 用例 + 新增等价性用例。

### 6.2 HSE DSP 移出首包 + idle 预热

**证据**：首包 `dist/assets/index-*.js`（1,650,674 B）里含 HSE 标记（`hyperplayer-v3-effects`、`hyperplayer:v3-params`）。引入链：`App.tsx:34` → `src/services/audio-engine/index.ts` → `engines/v3.ts` → `V3Adapter.tsx:10-17` → `attachV3Engine.ts:16-18`（`./src/index` 桶 + `EngineV3`）。而它**只在首次建音频图时才需要**（`useAudioPlayer.ts:342` 的 `ensureAudioGraph` → `390` 的 `onAudioGraphReady`，由 play 路径触发）。

**改法**：`V3Adapter` 内把 `attachV3Engine` 系改成动态 `import()`（模块句柄缓存，`attach/setParams/renderStudio/exportMp3` 共用），并在 `preloadOnIdle` 里预热该 chunk（首次播放前已就绪，避免「启动快了、首次播放变慢」）。调音室 UI 已经是 `lazy`。

**收益**：首包减小、启动解析更快。**风险**：中（必须保证 attach 一定在首次播放前完成；`attach` 本身已是 async 且失败会降级为直连，不影响播放）。**验收**：首包体积 + 启动日志 + 播放/音效全链路手测 + `npx vitest run src/services/HyperSoundEngine-v1`。

### 6.3 字体按需加载（打包体积 −9.4 MB）

**证据**：`src/assets/fonts/LXGWWenKai-Regular.woff2`（**8,281,292 B**）与 `SmileySans-Oblique.ttf.woff2`（**1,150,924 B**）通过 `src/assets/fonts/fonts.css` 被 `src/main.tsx:4` 与 `src/desktop-lyrics/main.tsx:4` 静态 import，占 `dist` 39 MB 中的约 9.4 MB。而**默认字体栈并不包含它们**（`FontPicker.tsx:42-48` 的 `fontStack('')` 回退到系统栈），只有用户**展开字体下拉预览**（`FontPicker.tsx:335` 用 `fontStack(option.value)` 渲染每一行）或**选中内置字体**（桌面歌词窗 `DesktopLyricsApp.tsx:430`）时才真正需要。

**改法**：把 `@font-face` 从全局 CSS 移到**运行期按需注入**（`new FontFace(...)` + `document.fonts.add`），仅在字体下拉展开或选中内置字体时加载；选中后 `document.fonts.load()` 预热避免首帧跳变。**许可证（OFL 1.1）与字体文件本身不变。**

**收益**：`dist` 39 MB → ~29.7 MB，asar / 安装包 / 热更包同步变小；默认路径零行为变化。**风险**：低–中（**必须覆盖「老用户已把霞鹜文楷设为歌词字体」这条路径**，否则字体会静默回退到系统栈＝可见回归）。

### 6.4 `backgroundThrottling` 策略

**证据**：主窗口 `backgroundThrottling:false`（`main.cjs:2160`，注释写明是「Chroma 后台联动」）；桌面播放器窗 `503`、桌面歌词窗 `694` 同为 `false`；启动页未设。后果：**窗口最小化后 rAF/定时器仍全速跑**。（渲染侧多数可视化已自行按 `visibilitychange` 停帧，但整体仍是全速。）

**改法**：默认改为节流（不设或 `true`），仅当**存在灯效插件消费者**（Chroma / SignalRGB 激活）或**桌面窗开启**时用 `webContents.setBackgroundThrottling(false)` 运行时打开。

**收益**：中（最小化后 CPU / 电量下降）。**风险**：中（**会改变最小化时的律动与灯效表现**，属可见行为变化，需产品决策）。**验收**：最小化 5 分钟对比 CPU；恢复后律动/灯效正常。

### 6.5 构建配置微调

- **`build.target`**：`vite.config.ts` 未设 → 用 Vite 6 默认（面向一堆老浏览器）降级转换。Electron 42 = Chromium 148，可设 `build.target: 'chrome148'` 去掉无谓转换。**风险**：低。
- **`manualChunks`**：目前只有 `vendor-react` / `vendor-motion` / `vendor-leaflet` 三组（`vite.config.ts:56-61`），`three` / `pixi.js` / `hls.js` 落在自动 chunk 里。补分组可改善缓存命中与加载组合。**风险**：低。
- **`sideEffects`**：`package.json` 未声明 → 打包器只能假设所有模块都有副作用。**但本项目有大量 CSS 副作用导入**，声明不当会**丢样式**。**建议单独提交 + 全量视觉回归**，或干脆不做。
- **`splitCityData` 重复写盘**：`scripts/split-city-data.mjs:58-65` 每次 build/dev 都删除并重写 192 个 JSON（约 14 MB）。可加「内容未变则跳过写入」，只影响**构建耗时**，不影响运行时。

### 6.6 Electron 运行时改造（✅ 已完成：2026-10-04 升级 Electron 44.5.0，未自编译）

- **最终决策**：不自编译。官方 **Electron 43+ 已自带**启动性能关键项——Node.js startup snapshot（43 引入、44 扩展到全部平台 #52879）与 V8 code cache（框架 bundle + preload 脚本预编译）；44 还降低了 Node.js 定时器引起的主进程空闲 CPU 唤醒。自编译只为「默认 flag」类收益需付 2-6 小时/次的编译成本，不成比例。
- 现状：官方 stock **Electron 44.5.0**（Chromium 152.0.7977.54 / V8 15.2 / Node 24.18.1；42.8.0 曾为 Chromium 148 / V8 14.8 / Node 24.18）。
- 配套改动：`vite.config.ts` `build.target: 'chrome152'`（升级 Electron 后必须同步）；V8 编译缓存目录按大版本分段 `userData/v8-compile-cache/electron-<major>`；启动裁剪 `disable-plugins`/`disable-extensions`/`disable-background-networking`；`registerFileProtocol` → `protocol.handle`（-6→404、-2→400，消费方 try/catch 兜底语义等价）。
- 打包链零改动：`build.electronDist` 仍指 `node_modules/electron/dist`；本机下载 44 zip 用 `ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/ node node_modules/electron/install.js`（postinstall 在本机不生效）。
- 44 的 breaking changes（移除 Windows ia32 / Linux armv7l、macOS 登录项 API）对本项目零影响。
- **仍留作独立立项的**：源码级魔改（改 Chromium/V8 C++、自编译 LTO）——当前瓶颈全部在应用层（已由 §3–§6 覆盖），没有必须改 C++ 才能拿到的收益；若未来确需（如裁剪渲染后端、定制合成器），再按「独立分支 + 保留官方运行时回退 + CI/本地不一致风险」评估。

## 7. 明确不采纳（附理由，避免反复讨论）

| 清单措施 | 决定 | 理由 |
|---|---|---|
| 二.4 `--expose-gc` + `global.gc()` | **不做** | 主动 GC 会引入毫秒级停顿；这是音乐播放器，对音频连续性（尤其无缝衔接/交叉淡化）最敏感，人为触发 GC 的风险 > 收益。V8 分代 GC 已足够 |
| 二.7 墓碑机制（杀渲染进程，再访问重载） | **不适用** | 会直接打断播放；本应用是「主窗口 + 按需辅助窗」模型，没有大量后台页面需要回收 |
| 二.8 进程合并 | **不适用** | 启动期渲染进程已最小化到 2 个（启动页 + 主窗口），桌面小窗/歌词窗延后 1.5s 按需创建、任务栏小窗懒创建。合并只会拿隔离性换微小收益 |
| 二.10 Windows `EmptyWorkingSet` | **不做** | 需要原生调用/FFI，违反「零原生依赖」的打包约束；且被换出的页在恢复时还要重新换入，反而引入卡顿 |
| 二.11 内存阈值熔断（自动刷新页面） | **不做自动动作**，仅保留观测 | 自动刷新页面＝打断播放。改为 `HYPERPLAYER_PERF=1` / `hyperplayer:perf-trace` 的可选指标（§2.2/§2.3）由人判断 |
| 三.7 原生 DOM API（`getElementById` 优于 `querySelector`） | **不做** | 本应用没有相应热路径场景（无逐帧 DOM 查询），收益可忽略而改动面大 |
| 五.3 动态切换图片格式（按性能选 JPEG/WebP） | **不做** | 封面格式由平台 CDN 决定；B 站 CDN 有防盗链（见 `index.html` 的 `no-referrer` 注释），改写图片 URL 有 403 风险 |
| 四.5 SharedWorker 共享通信通道 | **不适用** | 单窗口架构，不存在多个页面共享通信的需求 |
| 六.3 Monorepo / Turbo 增量构建 | **不适用** | 单包仓库，没有多包并行构建的场景 |
| 七.1 C/C++ 原生模块 | **不做** | 引入原生 addon 会带来 ABI 绑定、CI 构建复杂度与打包风险；当前没有必须用 C++ 才能解决的瓶颈 |
| 七.2 Rust → WebAssembly | **不做** | HSE 的实时 DSP 已经跑在 AudioWorklet 线程（不占 UI 线程），把纯 TS DSP 重写成 WASM 的收益与工程量/风险不成比例 |
| 长列表全量虚拟化 | **暂不做** | 先试 `content-visibility`（§5.2 第 1 步），确认不够再上虚拟化，避免一次性引入大量虚拟化回归 |

## 8. 红线（优化期间**不得**触碰）

1. **端口**：`3210`（Vite）/ `3211`（后端，仅 127.0.0.1）。闸门 `npm run check:ports`（已接入 CI）。落点散在 `vite.config.ts`、`package.json`、`local-server.mjs`（默认端口 + CORS 白名单 + SSRF 放行自身端口）、`desktop/main.cjs`（`BACKEND_PORTS` + 健康检查 + 放行 origin）、`scripts/dev-electron*.mjs`、`src/services/apiConfig.ts`。
2. **依赖分区与打包排除规则**：前端库必须留在 `devDependencies`；`build.files` 的四条排除规则（`!build/ui/**`、`!build/ui-clone/**`、`!**/*.map`、`!node_modules/@neteasecloudmusicapienhanced/api/public/**`）不得删除。闸门 `npm run check:packaging`（asar 预算 130 MB）。
   ⚠️ 注意：网易云的 `qrcode` / `dotenv` 是**真运行期依赖**（库用 `readdirSync` 动态加载 `module/*.js`），不能因为静态看不见就移到 dev。
3. **打包三大约束**：`vite.config.ts` 的 `base` 必须保持 `'./'`；`build.files` 必须含 `logo.png` 与 `build/**/*`；`build.electronDist` 保持 `node_modules/electron/dist`。
4. **启动页两段式时序契约**（`main.cjs`）：`SPLASH_ENTRANCE_FALLBACK_MS`（锚**起播**时刻，不是窗口显示时刻）、`SPLASH_START_MAX_WAIT_MS`、`SPLASH_MIN_VISIBLE_MS`、`splashGate` 三条件、以及「阶段一只停在第 0 帧」的设计——**一个都不要改**。
5. **设置镜像机制**：往简约模式设置里新增**全局**功能开关时，必须同步在 `src/services/globalSettingsRegistry.ts` 登记，否则传统/探索/桌面模式看不到。简约模式专属的外观设置不需要登记。
6. **后端安全不变量**：cookie 单事实源（全局 `qqMusicCookie` 只在显式登录/设置接口更新，播放/读取路由用 `resolveRequestCookie`）；`/api/cover` ↔ `/api/proxy-image` 的内网代理链必须继续放行 `localhost:3211`；Wallpaper Engine 预览/媒体的路径 containment；`server/local-service-auth.mjs` 的 constant-time 校验。
7. **配置隔离**：userData 恒为 `%APPDATA%/HyperPlayer`（禁止回退公共 `%APPDATA%/Electron`）；`appId`/IndexedDB 库名/token 变量名不得复用 WaveForge 旧值；`desktop/chroma-app-list-repair.cjs` 的 `STALE_APPS` 里**故意**保留的 `WaveForge*` 条目不要删。
8. **HSE 许可证**：`src/services/HyperSoundEngine-v1/` 内的 `LICENSE` / `授权补充说明.md` / `THIRD_PARTY_NOTICES` / 版权声明**不得删改**；对外命名统一 HyperSoundEngine（HSE），但代码标识符（目录名、类名 `EngineV3`、localStorage 键）不要重命名。
9. **启动页与窗口公共几何**：`desktop/splash.html` / `splash-baked.webm` 是生成物，勿手改；窗口位置恒居中（`centerBoundsInWorkArea`），勿改回「照搬记忆位置」；启动页舞台几何按视频自身比例 cover，**勿写死 16:9**。
10. **构建期间不要编辑任何会被打包的文件**：electron-builder 先按 stat 尺寸写头部、后拷贝内容，中途改动（哪怕只改注释）会静默产出「Node 能读、Electron 拒载」的坏 asar（症状：启动停在 Electron 默认页）。闸门 `verify-asar`。
